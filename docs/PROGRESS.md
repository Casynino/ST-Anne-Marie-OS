## Phase 3 — Exams, grading & results: BUILT (verified locally, 2026-10-20)

**What exists.** Configurable grading scales (bands, points, divisions, pass mark; per level or school default) and a results policy (absent = excluded or zero, rank by average or total, decimals, "all marks before submit") under `/grading`; examinations per term with weight and deadline (`/exams`), classes/subjects added in one step (one submission unit per stream); mark entry grid (`/marks/[id]`, mobile-friendly, live grade preview, Enter moves to next row, errors per student, nothing saved if any mark is invalid); workflow DRAFT → SUBMITTED → APPROVED → LOCKED with RETURNED for corrections; approval queue and bulk approve/lock; class results sheet (`/results`) with subject results, totals, averages, class/stream positions, divisions, class mean and a "complete / incomplete" banner.

**Rules built in (decided, change only on Nino's word).** A missing mark is "not entered", never zero; Absent/Exempt are explicit. Locking snapshots each mark's percent/grade/points/scale, so later scale edits never change locked results; unlock needs `results.unlock` and a reason (audited), clears the snapshot and sends the unit back as RETURNED; every edit after the first submission is written to the append-only `result_changes` table. Official results count LOCKED units only; "provisional" also counts APPROVED; units not yet counted are left out of totals (never zero) and reported in the coverage line. Teachers enter marks only where they are subject teacher (class, stream, subject) or class teacher (any subject of that class/stream) in the exam's year; `marks.enter_any` lifts that. Class results: `results.read` or the class teacher of that class/stream. Competition ranking (1,2,2,4) after rounding; rounding half away from zero. Division = sum of best N subject points, "INC" with fewer than N graded subjects.

**Nothing official is hard-coded.** The only built-in content is an optional, clearly labelled template (Tanzania O-Level CSEE pattern) that only pre-fills the new-scale form; it is applied only when someone saves it. **The school must confirm its grading bands, divisions, pass mark and weights.**

**Verification.** `tsc` clean; 204 automated tests (19 engine/validator unit tests; 15 integration tests: permissions and scope, validation all-or-nothing, workflow states, concurrent-edit detection, snapshot immutability, audited unlock, post-submission history, class results/positions/divisions, cross-school isolation); browser run on a throw-away database (entry, validation errors, submit blocked until complete, approve, lock, results sheet). ## Phase 5 — Fees & finance: BUILT (verified locally, 2026-10-20)

**What exists** (`/finance`): fee items and fee structures per class, level or everyone (most specific wins; lines can be every term or one term only), scholarships/discounts per student and year, bulk term-invoice generation with a preview and idempotent re-runs, one-off invoices, adjustment lines, instalment schedules, void; payments (cash, bank, mobile money) with numbered receipts, reversal, refunds (request → approve by someone else → mark paid), expenses with categories, arrears with ageing, collections by method and day, collection by class, expenses report, CSV exports, receipt and invoice PDFs (EN/SW), a reconciliation queue for provider notifications, a provider webhook endpoint, the optional financial-clearance rule for report cards, and a fees view in the family portal (invoices, payments, receipts, how to pay).

**Money rules (decided, do not change without Nino).** Money is DECIMAL(14,2) in the school currency (TZS) and integer cents in code; nothing adds floats. One balance service (`src/lib/finance/ledger.ts` + `src/server/balances.ts`) computes everything from live invoices, POSTED payments and active refunds. Allocation is derived, never stored: a payment aimed at an invoice pays it first, everything else is applied to invoices oldest first (issue date, due date), never more than an invoice owes; the rest is unapplied credit; refunds can only take credit and reserve their amount when requested. Zero charge, unpaid, partly paid and paid are separate states (a zero-total invoice is never "paid"). Originals are never edited: invoice lines are append-only (DB trigger), payments can only go POSTED → REVERSED with a reason (DB trigger, no delete), receipts only get a void marker, refunds need a different approver (DB CHECK too), expenses and provider events cannot be deleted. Payments are idempotent (client key) and the same bank slip / transaction reference cannot be posted twice; all money movements for one student are serialised with an advisory lock. Reversing a payment is refused if its money was refunded. Permissions: accountant records/reverses payments, generates and adjusts invoices, requests refunds and records expenses; head teacher grants discounts and approves refunds; only Super Admin holds everything.

**Provider notifications.** No provider is chosen and no credentials exist, so every provider (Selcom, AzamPay, ClickPesa, bank) is "not connected" until `PAYMENTS_<PROVIDER>_WEBHOOK_SECRET` is set; the endpoint then accepts only HMAC-SHA256-signed bodies (X-Signature), stores each event once (retries are harmless), and records a payment only for a verified SUCCESS event that matches exactly one student (admission number or invoice number) in the school currency; pending/failed events never create money; anything unclear waits in the reconciliation queue for a person. The neutral payload format is in `src/lib/payments/providers.ts`; the provider-specific signature and field mapping, and starting a payment from the system (STK push/checkout), are NOT built because they need the chosen provider's documentation and credentials. Nothing is ever shown as paid because a payment page was opened.

**Verification.** `tsc` clean; 285 automated tests (new: ledger unit tests including a 400-case randomised conservation/no-over-allocation check, discount maths, money parsing; 33 finance integration tests: permissions, structures, discounts, generation idempotence and concurrency, payments (partial/over/targeted/idempotent/duplicate reference/parallel), reversals, DB guards, refunds (two people, credit-only, reservation), adjustments, instalments, void, clearance, expenses, webhook (bad/unknown/unconfigured/tampered, duplicates, concurrent duplicates, pending/failed, unmatched, invoice-number match, reconciliation), cross-school isolation; 7 report/PDF/portal tests). Browser run on a throw-away database: all finance pages render, payment form validation and recording, receipt PDF/CSV routes, signed and unsigned webhook calls over HTTP, parent sees fees and receipts, parent blocked from `/finance`. PDFs checked visually (two layout overlaps found and fixed). Throw-away database dropped.

**Open.** Provider integration (needs the school's chosen provider + credentials); SMS/e-mail fee reminders (Phase 6); fee-balance widgets on role dashboards and PDF/Excel exports (Phase 7); students are matched in the reconciliation screen by search, not by scanning; no late-fee/penalty rules (not requested); refunds only for unapplied credit (a withdrawal refund is done by adjusting the invoice first); one payment belongs to one student (a family payment is entered once per child).

## Phase 8 — Hardening & launch: BUILT (verified locally, 2026-10-21)

**Backups.** `npm run db:backup` takes a consistent snapshot of the database (pg_dump custom format from one exported snapshot), checksums it, records the checksum and the row count of every table in `backup_runs` (append-only by DB trigger; a success without checksum/size is refused by a CHECK), optionally copies it to the S3 bucket, and keeps the newest 14 local copies. `npm run db:backup -- --verify` restores a dump into a scratch database whose name ends in `_restore` (anything else is refused), checks the file against its recorded checksum and compares every table's row count; the result (success or failure) is recorded. Tested here: backup, restore test, a tampered file is detected and recorded as failed, an unsafe target is refused, the records cannot be edited or deleted. **Settings → Backups** (Super Admin) shows the newest backup, the last restore test and the history, and the dashboard warns when the newest backup is older than 26 hours or none exists. Running it nightly needs a computer or job with the PostgreSQL client tools (`docs/DEPLOYMENT.md` section 5, `docs/backup-workflow.example.yml`); the web app does not and cannot make backups itself.

**Security.** Production Content-Security-Policy (own origin only, no framing, no plug-ins) on top of HSTS, nosniff, frame, referrer and permissions headers (checked on a production build, pages load without violations). Automated source guards: every API route must authenticate (session, cron secret or signed webhook) and every server action must go through the permission-checked wrapper; no database password, token or private key may be committed; session cookie is HttpOnly / SameSite / Secure in production. Existing protections unchanged: scrypt passwords, hashed session tokens, DB-backed sign-in rate limiting, server-side permission checks, append-only audit trail.

**Performance (laptop database, 5,000 students, 5,000 invoices, 3,000 payments).** Student list and searches ≈ 7 ms; dashboard ≈ 1.1 s; finance overview 0.5 s; arrears 0.6 s; invoice list 0.6 s; term invoices for 5,000 students generated in 5 s; 5,000-row export (CSV/Excel) < 0.2 s; a 60-card report PDF 0.3 s. Seeding 5,000 students took 17 s. The finance and dashboard calculations are done in application memory, fine at this size; move them into the database beyond about 20,000 invoices per term.

**Documentation.** `docs/DEPLOYMENT.md` (hosting map, environment variables, first production setup, release procedure, backups and restore, security checklist, honest limits), `docs/manuals/` (administrator, teacher, accountant, parent and student guides, English and Kiswahili; the Kiswahili was written by the assistant and needs a native read-through).
