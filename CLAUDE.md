# St Anne Marie Schools OS

School management system for St Anne Marie Schools (Tanzania). Real operational system: never add fake students/payments to production. Full requirements digest: `docs/REQUIREMENTS.md`. Build status and next steps: `docs/PROGRESS.md`. Global rules in `~/.claude/CLAUDE.md` apply (notably: **never `git push` or deploy unless Nino says "push"**; commit locally is fine).

## Stack
Next.js 16 (App Router, Turbopack) · TypeScript strict · React 19 · Tailwind 4 · Prisma 7 + `@prisma/adapter-pg` · PostgreSQL (local 16 for dev/test; Neon for production) · Zod 4 · Vitest. No Redis, no separate backend. Node ≥ 22.18.

## Commands
- `npm run dev` — dev server (port 3000). `npm run build` — `prisma generate` + `next build`.
- `npm run typecheck` · `npm test` (all) · `npm run test:unit`.
- `npm run db:migrate` — dev migration (interactive; hangs in non-TTY, so use `prisma migrate dev --create-only` then `migrate deploy`/`migrate dev`). `npm run db:bootstrap` — idempotent: permission catalog, school `SAM`, default roles, first Super Admin from `BOOTSTRAP_ADMIN_*` env (only if the school has no users).
- Drift check (non-interactive): `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script < /dev/null` must print an empty migration.

## Environment (Phase 2 additions, see `.env.example`)
`STORAGE_DRIVER` (`local` dev only | `s3` for R2/S3-compatible; unset in production = uploads refused), `STORAGE_LOCAL_DIR`, `S3_*`, `DOCUMENT_MAX_BYTES` (default 4 MB), `CRON_SECRET` (Bearer secret for `GET /api/jobs/notifications`). `NEXT_DIST_DIR` lets a second Next server (e.g. a smoke copy on a throw-away database) run beside the main dev server.

## Architecture (follow these conventions)
- `src/server/*` = domain services. Every function takes `ctx: AuthContext` and: checks permission (`requirePermission`) → scopes every query by `ctx.schoolId` (other-school records ⇒ `NOT_FOUND`) → validates with zod (`parse`) → writes in a transaction with `writeAudit(tx, …)`. Business rules live here, never in components.
- `src/lib/auth/*`: scrypt password hashing, DB sessions (hashed token cookie `sam_session`), DB-backed login rate limiting, `buildAuthContext` loads permissions per request. `src/lib/auth/next.ts` = Next glue (`requireContext`, `getT`).
- RBAC: permission catalog in `src/lib/rbac/permissions.ts`, default roles in `roles.ts`; synced to DB by `syncPermissionCatalog`/`ensureSchoolRoles` (never re-grants permissions an admin removed). No privilege escalation: you can only grant/assign what you hold. Portal roles `parent`/`student` are not staff-assignable.
- Server actions: `src/app/**/actions.ts` use `run(form, fn)` from `src/lib/action.ts` (auth, parse FormData, map `AppError` to field errors, generic message for unexpected errors). Forms: `ActionForm`/`Field` in `src/components/form.tsx`.
- i18n: `src/lib/i18n/en.ts` + `sw.ts` (same keys; parity test). All UI strings go through `t()`.
- Dates: `@db.Date` for calendar dates, helpers in `src/lib/dates.ts` use UTC to avoid shifts; school timezone for "today".
- Unique rules Prisma can't express (partial/NULLS NOT DISTINCT indexes, CHECKs, audit trigger) are in the init migration SQL; the NULLS NOT DISTINCT indexes are also declared in `schema.prisma` with `map:` so Prisma doesn't drop them.
- Page files must only export `default`/`metadata` (put helpers in separate modules).

## Phase 2 architecture (Admissions & Attendance)
- **Attendance** (`src/server/attendance.ts`, reports in `attendance-reports.ts`): `AttendanceRegister` per class/stream/session/date (DRAFT|FINALISED) owns `StudentAttendance` (unique student+session+date, stricter than student+class+date+session). Finalised registers change only via `correctAttendance` (needs `attendance.correct`, reason, append-only `attendance_corrections` table) or conflict resolution. Sessions: `school_settings.attendance` (`mode` DAILY default | PER_SESSION) + `attendance_sessions` (DAY always exists).
- **One write path** for online form and offline sync: `submitAttendance` (idempotent on client-generated `clientOpId` per user via the `attendance_operations` ledger; advisory lock per register; conflicts are stored, never silently applied). Policy: keep first finalised record; a later divergent submission becomes a CONFLICT reviewed on `/attendance/conflicts` (accept = audited corrections, dismiss = keep server). Students with no record yet (late joiners) can be added to a finalised register; existing records are never altered by a normal submission. Validation failures are NOT recorded in the ledger so the client can fix and retry with the same id.
- **Offline** (client-only, `src/lib/offline/*`, `src/components/attendance/*`): rosters downloaded explicitly into IndexedDB (per user, per date), outbox with states queued/syncing/synced/failed/conflict ("synced" only after the server answers APPLIED), `POST /api/attendance/sync` (same-origin check, cookie auth), `public/sw.js` (production only) caches `/offline-attendance` (a page with no user data) and `/_next/static/*` — nothing else. Sign-out clears downloaded lists but keeps unsynced operations.
- **Notifications** (`src/server/notifications.ts`): `notification_events` outbox, one per (absent record, guardian with `receivesNotifications`), dedupe key; processed with a lease + SKIP LOCKED right after finalise and by the cron route. Channels: in-app (only guardians with a portal user) and SMS through `src/lib/sms/adapter.ts` — no provider chosen, so SMS is recorded SKIPPED. Nothing is ever reported as delivered without a provider confirmation.
- **Admissions** (`src/server/admissions.ts`): Applied → (Interview) → Accepted → Enrolled, Rejected/Withdrawn need a reason. Accepted ≠ enrolled: `enrolApplication` runs `createStudentInTx` (shared with direct registration) in one transaction. Open duplicates blocked by service + partial unique indexes (migration SQL).
- **Documents** (`src/server/documents.ts`, `src/lib/storage/*`): type decided from file bytes (PDF/JPEG/PNG/WebP), size cap, random storage keys, downloads only through `/api/documents/[id]` (permission-checked, audited, `no-store`). Delete = hide + audit.
- **Import** (`src/server/import.ts`, pure logic in `src/lib/import/students.ts`, CSV parser `src/lib/csv.ts`): upload → preview batch (nothing imported) → confirm re-checks the DB and imports in ONE transaction, once per batch. CSV only (Excel: "Save as CSV UTF-8"; no spreadsheet dependency by design). Max 1,000 rows / 2 MB.
- Tests that need attendance use `createCurrentYearAcademics` (the year must contain today; future dates are refused).

## Decided business rules (Phase 1)
- One ACTIVE enrollment per student per academic year (DB-enforced); moves/year changes close the old row (`MOVED`/`COMPLETED`), history is kept. Status changes (transfer/withdraw/graduate) require a reason and close the active enrollment; reinstatement returns to Enrolled (class placement is a separate step).
- Student needs ≥1 guardian at registration; exactly one primary guardian; last/primary guardian can't be unlinked; changing a relationship clears its verification.
- Medical notes: read needs `student.medical.read`; editing needs read + update; note content is never written to the audit log (views are audited).
- Teachers (`student.read_assigned`) only see students in classes/streams they teach in the current year.
- Duplicate student (same name + DOB) and shared guardian phone require explicit confirmation.

## Decided business rules (Phase 2)
- Attendance default: ONE session per day (`DAY`); per-session mode is a setting. **Open decision for the school** (placeholders until confirmed): low-attendance threshold 85%; late counts as present; excused does NOT count as present in the rate; correction rights are `attendance.correct` only (Head Teacher by default; no time window); conflict policy = keep first finalised, flag later (proposal, not yet confirmed).
- Roster for a date = enrolments with `startedOn <= date < endedOn` in that class/stream; attendance can't be recorded for future dates or dates outside an academic year; finalising requires every student on the list to be marked.
- Take attendance: `attendance.take` = classes/streams the staff member teaches (class OR subject teacher assignment); `attendance.take_any` = all. Reports/registers visible with `attendance.read` (all) or `attendance.read_assigned`.
- Absence alerts are created only for ABSENT (not Late/Excused), per guardian with `receivesNotifications`; a correction away from Absent cancels a still-pending alert; one event per record+guardian ever.
- Applicant duplicate rules: an OPEN application for the same child (name+DOB or birth certificate) is refused outright; a matching existing student needs explicit confirmation. Application numbers `APP/<year>/<seq>` come from the shared counter table (scope `APP:<year>`).
- Import: error and duplicate rows are never imported; shared guardian phones need explicit confirmation and never link to the existing guardian; same guardian name+phone inside one file = one guardian (siblings); admission numbers given in the file are kept and must be unique, generated ones skip taken numbers; dates are day-first.

## Phase 3 architecture (Exams, grading & results)
- Services: `grading.ts` (scales, results policy in `school_settings.results`, `resolveScale`: exam scale → level scale → school default; optional template only pre-fills a form), `exams.ts` (exam + exam subjects; creates one `ResultSubmission` per stream, or one whole-class unit), `marks.ts` (access scope, mark sheet, `saveMarks` all-or-nothing with row lock + optional `expectedVersion`, submit/approve/return/lock/unlock, `bulkTransition`, `markHistory`), `results.ts` (`computeClassResults` internal, `getClassResults` permission-checked). Pure maths in `src/lib/results/engine.ts`; typed-mark validation in `src/lib/results/entry.ts`.
- Rules: missing mark ≠ zero; Absent/Exempt explicit; only DRAFT/RETURNED are editable; lock snapshots `locked*` on `marks`; unlock needs a reason and clears snapshots; edits after first submission go to append-only `result_changes`; official results count LOCKED units only (PROVISIONAL adds APPROVED). Teachers: subject teacher (class+stream+subject) or class teacher (any subject of the class/stream); `marks.enter_any` is all. Class results: `results.read` or class teacher.
- Roster for a unit = enrolments in the class (and stream) that overlap the exam's term.
- UI: `/exams`, `/exams/[id]`, `/marks`, `/marks/[id]` (client grid `src/components/results/mark-grid.tsx`), `/results`, `/grading`. Multi-button forms use `SubmitButton` (`intent`).

## Phase 5 architecture (Fees & finance)
- Money: DECIMAL(14,2), integer cents in code (`src/lib/finance/money.ts`). ONE balance calculation: `computeLedger` (`src/lib/finance/ledger.ts`) fed by `loadFinance`/`loadStudentFinance` (`src/server/balances.ts`); never sum fees anywhere else. Allocation is derived (targeted payment first, then oldest invoice first, no over-allocation, credit left over, refunds only from credit).
- Services: `fees.ts` (items, structures, discounts, settings key `fees`, `clearedStudents`), `invoices.ts` (term generation, one-off, adjust, instalments, void, lists, statements, `allocateNumber` INV/RCT via `admission_counters`), `payments.ts` (`postPaymentTx` shared by manual entry, provider events and reconciliation; reversals; refunds), `expenses.ts`, `payment-events.ts` + `src/lib/payments/providers.ts` (webhook, reconciliation), `finance-reports.ts`, `finance-pdf.ts` + `src/lib/pdf/finance.ts`. Webhook: `POST /api/payments/webhook/[provider]`. PDFs: `/api/receipts/[paymentId]`, `/api/invoices/[id]`; CSV: `/api/finance/export`.
- Integrity is also in the database (migration `phase5`): append-only invoice lines, payment/receipt/provider-event guards, refund requester ≠ approver CHECK, partial unique indexes (one live term invoice per student+term, one active structure per scope, posted reference, idempotency key). Never edit these records; reverse, void or adjust.
- Report-card publishing uses `clearedStudents` (needs a bill for the term and outstanding ≤ the school's limit) when "require fees cleared" is on.
- Permissions: `fees.read|manage|discount`, `invoice.generate|adjust|void`, `payment.record|reverse`, `refund.request|approve`, `expense.read|manage`, `finance.reports`, `finance.reconcile`.

## Phase 6 architecture (Communication)
- Everything sent to a parent is a `notification_events` row (outbox) processed by `processPendingEvents` (lease + SKIP LOCKED, times compared in UTC). Types: ABSENCE, ANNOUNCEMENT, FEE_REMINDER (from a `Broadcast`), RESULTS_READY (`createResultsReadyEvents`, called inside `publishReportCards`). `renderEvent` builds title/body per type and the guardian's language; preferences (`notification_preferences`) and per-message channel flags decide SKIPPED. SMS only through `getSmsAdapter()` (not configured now); delivery reports via `src/server/sms-reports.ts`.
- `communication.ts`: templates (`message_templates`, variables whitelisted per key), audiences (`resolveRecipients`), `previewBroadcast`/`createBroadcast`/`cancelBroadcast`, preferences. Permissions: `comms.read|send|fee_reminder|manage`, `messages.read|send|moderate`.
- `messaging.ts`: threads between a parent and a teacher/office, moderation, scope checks (`teachingScope`), rate limit. `calendar.ts`: term dates + `school_events` (internal events are staff-only). Staff calendar lives at `/school-calendar` because the public site owns `/calendar`.
- Route rule: a path may exist in only one route group; run `NEXT_DIST_DIR=.next-build npx next build` after adding routes.

## Phase 13 architecture (Digital Library and school IDs)
- **School IDs** (`src/server/school-ids.ts`): student ID = `Student.admissionNo` (generated at official enrolment, existing numbering reused, never changed); staff ID = `Staff.staffNo`, allocated in `createStaffUser` from `admission_counters` scope `STF:<year>` with the pattern in setting `staff_id` (default `{PREFIX}/STF/{YEAR}/{SEQ}`; edit in Settings), immutable, never reused. `assignMissingStaffIds` backfills (idempotent, audited; button in Settings). `findBySchoolId` / `normaliseSchoolId` tidy typed IDs.
- **Library** (`src/server/library.ts`, rules in `src/lib/library/access.ts`, files in `files.ts`, viewer glue in `next.ts`): resources have a status (DRAFT, PENDING_REVIEW, APPROVED, PUBLISHED, ARCHIVED; approver is never the uploader; setting `library.requireApproval`), an audience (PUBLIC, STUDENTS, STAFF, CLASSES, SUBJECTS, RESTRICTED), optional release date, and versioned files (`library_files`, one current; replace keeps history). **Access is decided in ONE pure place** (`canAccess` / `canDiscover`) and mirrored by the SQL filter `visibilityWhere`; an integration test asserts they agree. Anything not permitted is not listed, and a direct URL answers like a missing item. Staff-only and restricted material is never listed to students or visitors.
- **Who is who** (`src/server/library-identity.ts`, cookie `sam_lib`, table `library_sessions` stores only a hash): a visitor sees public material and the student list (files locked); a student proves School ID + PIN (`library_pins`, hashed, set by the school per class at `/library-admin/students`); a teacher proves staff ID + account password (the ID alone never opens staff material); a signed-in staff account is recognised without asking again. ID-only access exists only when setting `library.allowIdOnly` is on AND the resource is marked `idOnly` AND the person is a student. Failures are generic ("could not verify") and rate limited per IP and per ID (`lib:ip`, `lib:id`).
- **Delivery**: only `GET /api/library/files/[id]` (and `/covers/[id]`) streams the file (`storage.stream`, Range support, `private, no-store`, inline for PDF and images, `?download=1`, staff `?v=` previews); there is no public file URL. Allowed opens of PUBLISHED resources are counted (`library_events`, append-only); staff previews are not; refusals are logged only for identified people. Activity is shown at `/library-admin/activity` (needs `library.manage`).
- **Screens**: public `(site)/library` (landing, search, resource page, verify); staff `(app)/library-admin` (list, new, resource workflow, categories, statistics, student PINs, settings, activity). Permissions `library.read|upload|review|publish|manage|access_staff|analytics|pin`, `schoolid.manage`; a new permission needs `npm run db:bootstrap` on each database.
- **Limit**: uploads go through the app (25 MB local; Vercel refuses request bodies over ~4.5 MB), so large files in production need a direct-to-storage (presigned) upload that is not built yet.

## Admission examinations, school fee and registration (decided 2026-10-21, Nino's brief)

Permissions: `admission.exam.assign` (registrar, academic office, head), `admission.exam.mark` (class/subject teacher, only their own tasks, only after the interview time), `admission.exam.review` (academic office, head). Teacher must be an active staff user who may mark and is offered in this order (`teachersFor` in `src/lib/admissions/exams.ts`, used by the screen and by `assignExam`): the teachers recorded for the subject in the class the applicant applied for (current year), else those recorded for it anywhere, else any teacher who may mark. The workspace lists each assigned subject with Change teacher / Remove (one assignment per subject, changing replaces it and keeps the history); the add form offers only unassigned subjects and several subjects can have different teachers. Policy keys (screen `/admissions/policy`): `examSubjects` (required for levels whose rule is Exam or Both), `examApproval`, `examMaxMark`, `examOutcomes`. A decision (`recordQuickResult`, `recordInterviewResult`, `acceptanceReadiness`) is refused until every required result is final (submitted, or approved when approval is on) — `assertExamsComplete`; every subject final counts as the entrance examination done. A submitted result changes only when a reviewer returns it (history keeps the old mark); nothing changes after the decision. Rescheduling moves the assignments to the new interview, cancelling withdraws unmarked ones. Policy `examAutoAccept` + `examPassPercent` (default off / 50): when every required result is final and the average reaches the pass mark the applicant is passed and accepted by itself (`src/server/admission-auto.ts`, called after the marks/approval are saved; runs `recordQuickResult` with the permissions of the person who reviewed the application, audit `admission.auto_accept`, never touches marks); a pass then goes to Awaiting payment, a result below the pass mark or a non-numeric outcome always waits for the office. Teacher screens: `/applicant-exams` (own tasks; offices see all) and `/applicant-exams/[id]`; sidebar badge and teacher dashboard panel. Marks are private to the teacher until submitted; comments are staff-only.
- **After the decision**: accepted ≠ registered. Admissions cannot record or verify admission payments (Finance does, existing ledger and gate). Registration (`enrolNow` / the Register button, `/admissions/accepted/[id]`) makes the ONE student record with the existing admission-number generator; a class is given afterwards in Class placement. The accepted page (`/admissions/accepted/[id]`) is where Register happens: it lists everything from the application form (edit via the application's Edit details), preselects the class applied for (`placementChoices`: least-filled stream, nothing preselected and a warning when the class is full; a full class is refused unless `class.capacity_override`), and calls `enrolApplication` with the class so the student gets the Student ID and the class together; **the class is required (Nino, 2026-10-22): registering a new student gives the Student ID and the class in ONE step** (`/admissions/registration` lists every cleared applicant with the class asked for preselected and a Register button on the row, `registerFromListAction`; `enrolApplicationAction` refuses a missing class for anyone who may place students). The Class placement list remains only for students who arrive without a class by other routes (import, direct registration). **Several at once** (`registerMany` in `src/server/admission-registration.ts`, `registerManyAction`): tick applicants (ticks kept in React state by `components/lifecycle/tick.tsx`, so a refusal does not clear them), choose ONE class (a stream, or "any stream" = the emptiest each time); if the class has fewer places than ticked applicants the whole request is refused up front, naming the classes that do have room, and nobody is registered; over the limit needs `class.capacity_override` and a reason; each applicant is otherwise handled on their own and reported by name with the Student ID. The panel "Where there is room" (`classRoom`) shows students, places left and waiting applicants per class. The Class placement tab is no longer in Admissions (the page remains, reached from a banner on the Students page). After registering, the same address shows `registeredSummary` (Student ID and class), never a 404. With no school fee a pass still registers at once. Not built: uploading answer sheets, teacher availability clash check.

## Joining instructions (Nino, 2026-10-21)
- An accepted (or registered) applicant has joining instructions: what to pay (the offer's fee, what Finance has verified, what is still owed, the payment reference = the application number, and "How to pay" exactly as typed in Fee settings), what to bring, when and where to report, the entrance results (marks only, never teachers' comments) and what happens next. `joiningView` (`src/server/joining.ts`) is the one source; staff (`admission.read`) open it by application id, the family by the id of their own application (the draft); anybody else gets "not found"; before acceptance it is a conflict. Screens: the `JoiningCard` (`src/components/admissions/joining-card.tsx`) on `/admissions/accepted/[id]` and on the family's `/family/applications/[id]`; the printable one-page letter (pdf-lib, EN + SW labels, school-typed text kept as typed) at `GET /api/applications/[id]/joining?lang=` (`src/lib/pdf/joining.ts`, `src/server/joining-pdf.ts`; each download audited). What the school wants to tell families (reporting date, time and place, what to bring one per line, notes) is setting `admission_joining`, edited on `/admissions/policy` (`school.settings.update`). Nothing is hard-coded.

## Year lifecycle: progression, returning students, annual fees (Phase 19, Nino's brief 2026-10-22)
- **One student, one record, one Student ID for all years.** Each year is three separate facts, each its own record, none a copy of another: the Academic Office's **decision** (`student_progressions`: PROMOTED, REPEAT, PENDING_REVIEW, COMPLETED, WITHDRAWN, TRANSFERRED; status DRAFT, AWAITING_HEAD, APPROVED, SUPERSEDED), Admissions' **annual registration** (`annual_registrations`: PENDING, REGISTERED, ACTIVE, CANCELLED; unique per student and year) and the **enrolment** (`student_enrollments`, created only when the registration goes ACTIVE through the existing `placeStudentTx`). Fee clearance is worked out, never stored.
- Pure rules `src/lib/lifecycle/rules.ts` (`nextGrade`, `examCompletion`, `promotionSignal`, `clearanceState`, `checkDecision`, `nextStep`, `placesLeft`, `recommendStream`). Services: `lifecycle-settings.ts` (setting `year_lifecycle`: `requireHeadApproval`, `promotionMinAverage` (null = none), `feePolicy` INFORM_ONLY | BLOCK_REGISTRATION | BLOCK_ACTIVATION, `previousDebtCounts`), `lifecycle-data.ts` (grades in order, years, `examCompletions` from LOCKED results, `yearFinances` from the one ledger), `progression.ts`, `annual-registration.ts`, `annual-fees.ts`, `year-readiness.ts` (checklist + `studentTimeline`).
- **Grades**: `classes.nextClassId` / `isFinalGrade` (screen: Academic setup > class > "Grade after this one": empty = next class in the school's order across levels, FINAL = finish school). Nothing hard-coded; the last class in the order is final. Year registration dates `academic_years.registrationOpensOn/ClosesOn` are informational (shown, not enforced).
- **The system never decides promotion or repetition.** With no promotion average set, `prepareProgressions` drafts everyone as PENDING_REVIEW; with one, only those who reach it are drafted PROMOTED/COMPLETED. Incomplete or missing results (`examCompletion`: every examined subject of the student's class/stream LOCKED and a result present), a grade outside the order, completing a non-final grade, or promoting below the configured average are **exceptions**: need `progression.exception` and a recorded reason (kept on the decision and in the audit). Bulk (`decideProgressions`, `approveProgressions`, max 300) handles each student in its own transaction and reports who was refused and why.
- **Approval**: `progression.approve` (Academic Office) makes a decision final; with `requireHeadApproval` it waits as AWAITING_HEAD for `progression.head_approve` (a Head Teacher approving gives both at once). Approved rows are immutable (DB trigger, no deletes); a revision (`reviseProgression`, `progression.exception` + reason, promoted/repeat only, refused once REGISTERED/ACTIVE) supersedes the old row and starts a new DRAFT. Final approval **applies** the decision: PROMOTED/REPEAT -> `ensureRegistrationTx` (creates or re-links the registration; `createMissingRegistrations` covers decisions approved before the next year existed); COMPLETED/WITHDRAWN/TRANSFERRED -> `applyStatusChangeTx` (shared with the Students status screen; closes the enrolment, effective min(today, year end)).
- **Registration desk** (`registration.manage`; `/students/returning`, `/students/returning/[id]` (in the Students area, NOT in Admissions: Admissions is only for new/onboarding applicants, Nino 2026-10-22)): `placeReturning` (decided grade preselected with the emptiest stream; another grade needs `progression.exception` + reason; capacity checked under `pg_advisory_xact_lock` per class and year counting the roster **and places already promised** to returning students; a full class needs `class.capacity_override` + reason), `confirmRegistration` (annual registration; checks fee clearance only when policy = BLOCK_REGISTRATION), `activateRegistrations` (joins the roster; refused before the year starts, or when policy = BLOCK_ACTIVATION and not cleared; uses `placeStudentTx(..., { capacityReserved: true })`), `cancelRegistration`/`reopenRegistration` (reason, never deleted). `assertCapacity` (new admissions, transfers) also counts reserved registrations and takes the same lock.
- **Finance** (`fees.read`; `/finance/annual`): clearance per returning student from verified payments only: first-term invoice of the year billed and outstanding <= `clearanceMaxOutstandingCents`; **older-year debt is a separate line**, counted only when `previousDebtCounts`. `billReturningStudents` = `generateTermInvoices(..., { returning: "on" })` (also bills placed returning students before they join the roster; idempotent). `fees.clearance.exception` records a payment arrangement (reason, person, time; withdrawable) that treats the condition as met **without changing any balance**. `RETURNING_PLACEMENT` (Admissions) and `RETURNING_FEE` (Finance) hand-off tasks; `syncFeeTasksForStudentTx` runs inside `postPaymentTx` and `reversePayment`. Admissions sees the clearance state and a "older debt" flag, amounts only with `fees.read`. Unpaid fees never reverse a promotion or placement and never block anything unless the school's policy says so.
- **Initial payment and follow-ups (2026-10-22)**: Fee settings has `initialPaymentPct` (empty = off): when set, a returning student's first-term condition is met once verified payments cover that share of the first-term bill (`yearFinances` computes `maxOutstanding` from it; otherwise `clearanceMaxOutstandingCents` as before). Parents see on the child's page a step tracker (decision, registration, initial payment, class and stream, in the class), the first-term bill, verified payments, what is still due, the initial payment needed, older-year debt on its own line and the school's own "How to pay" text (`familyRegistrationView().fees`); a payment counts only when Finance has verified it. `/family` shows each child's next-year state. Finance `/finance/annual` also filters by stream, decision (promoted/repeat) and registration status. **Not registered yet**: tab on `/students/returning` (registration still PENDING; banner turns amber after `registrationClosesOn`), with append-only follow-up notes (`registration_follow_ups`, `registration-followups.ts`, `registration.manage` writes, outcome Will register / Not returning / No answer / Something else; "Not returning" and "Something else" need a note). A note never cancels or withdraws anyone: cancelling stays its own reasoned step. Migration `phase21_registration_follow_ups`.
- Academic Office screens `/academic-office/progression` (+ `[studentId]`), checklist `/academic-setup/readiness`, student page card "Years at school", Academic Office alerts `progressionTodo`/`headProgression` (only near year end or once the next year exists). New permissions (8): `progression.read|prepare|approve|head_approve|exception`, `registration.read|manage`, `fees.clearance.exception`; run `npm run db:bootstrap` after migration `phase19_year_lifecycle` on each database. Tests: `tests/integration/year-lifecycle.test.ts` (29) and `tests/unit/lifecycle-rules.test.ts`. Not built: automatic roll-over of the current year, SMS/in-app notices to families about registration.

## Family registration for next year (Nino, 2026-10-22)
- A parent (or the student) registers the child for the coming year from `/family/[studentId]` (card "Next year"), once the Academic Office's PROMOTED/REPEAT decision is APPROVED: `familyRegistrationView` (what to show: OPEN, NOT_YET, CLOSED, FEES, REGISTERED, JOINED, CANCELLED) and `registerMyChild` in `src/server/annual-registration.ts`, action `registerChildAction` (`(portal)/family/actions.ts`). In ONE transaction it places the child in the decided grade (stream with the fewest students) and confirms the registration (the tick "we confirm that the child is returning and the details are correct"); `confirmations.via = FAMILY_PORTAL`, audit actor = the parent. Rules enforced: the registration window (`registrationOpensOn/ClosesOn` are enforced for families, informational for staff), class capacity (a full class is refused, never overridden: "contact the school office"), the fee policy `BLOCK_REGISTRATION` (Finance gets a `RETURNING_FEE` task), an existing placement by Admissions is kept, idempotent, only the child's own family (staff and other families get NOT_FOUND/forbidden). It does NOT put the child in the class roster: that stays Admissions' step when the year starts (`Join class` on Returning students). Tests: `tests/integration/family-registration.test.ts`.

- Dashboard data: `src/server/dashboard.ts` (school numbers) + `src/server/ops.ts` (`activityPanel`/`securityPanel` need `audit.read`, `systemPanel` needs `backup.read`; read-only, from `audit_logs`, `sessions`, `login_attempts`, `error_events`, `job_runs`, `backup_runs`).
